# 上线执行清单

> 从「手上一台服务器都没有」到「域名可以访问」的完整顺序。
> 平台细节与更新流程见 [deploy/README.md](../deploy/README.md)，
> 架构与数据边界见 [公开部署准备.md](./公开部署准备.md)，**本文不重复那些内容**。
> 本文只回答三件事：**买什么、填什么、验什么。**

## 一、买之前要做一个决定：节点选哪里

| | 中国内地节点 | 中国香港节点 |
| --- | --- | --- |
| ICP 备案 | **必须**，要等（数天到两三周） | **不需要** |
| 内地访问质量 | 好 | 可能波动 |
| 适合 | 已经下定决心长期做 | 想尽快看到线上效果 |

**建议**：先按「能不能今天就出效果」来选。
急着验证上线流程就用中国香港节点；确定要长期面向内地用户，就趁早走备案，因为备案是**最长的前置**，
越晚开始越堵。

备案期间可以先做两件事，不浪费时间：
1. 用 `<公网IP>.sslip.io` 免费地址先把整套环境跑通（Caddy 能给它申到 HTTPS 证书）。
2. 把短信通道配好（见第五节）—— 它也是 preflight 的必过项。

## 二、买什么

**服务器（轻量应用服务器即可，不必买 CVM/ECS 通用型）**

- 系统：**Ubuntu 24.04 x86_64**
- 规格：**2 核 2 GB 起**；系统盘 **≥ 40 GB**
- ⚠️ 2 GB 构建前端可能不够。要么加 2 GB 交换空间，要么直接上 4 GB。
  这一步别省 —— 构建到一半被 OOM 杀掉，报错信息很难看出来是内存问题。
- 安全组/防火墙：开 **80、443**，SSH 端口（默认 22，建议改）
- ⚠️ **8010 / 8011 绝对不要对外开放**。两个 Python API 只在 Docker 内网通信。

**域名**

- 有域名：把 A 记录指向服务器公网 IP。
- 没域名：先用 `<公网IP>.sslip.io`，它能解析到内嵌的 IP，Caddy 也能申证书。
  依赖第三方 DNS，长期要换自有域名。

**要花钱的第三方服务（账号侧的，不是服务器侧的）**

| 服务 | 用途 | 备注 |
| --- | --- | --- |
| DeepSeek API | 模型调用 | `MODEL_API_KEY` |
| 北大法宝 MCP | 法规与类案检索 | `PKULAW_MCP_TOKEN` + 14 个 `PKULAW_URL_*` |
| 阿里云号码认证服务 | 短信验证码 | 短信认证套餐包；见第五节 |

模型与 MCP 是**按量计费**，模板里已经把访客额度压到很低（每日 5 / 全站 30），
先观察账单再调，别一上手就放开。

## 三、服务器到手后的顺序

**服务器和域名到手之后，实际只需要两个值：**

```bash
deploy/deploy.sh --server ubuntu@<公网IP> --site-host <域名>
# 还没有域名时：
deploy/deploy.sh --server ubuntu@<公网IP> --site-host <公网IP>.sslip.io
```

这一条命令做完全部事情：生成 `.env.production` → 打法规库快照 → 装 Docker/rsync
→ 配镜像源 → 传代码/配置/快照 → 构建 → 起 backend/v3/frontend → 容器内跑预检
→ **预检全绿才起 Caddy**（开 80/443、申 HTTPS 证书）→ 对着公网地址跑一遍验收。

只想在本机先验一遍脚本本身（不碰服务器）：`deploy/deploy.sh --local --skip-caddy`。

### 想手工走一遍（排错时用）

脚本里每一步都能单独重跑，顺序不能颠倒：

```bash
python3 deploy/render_env.py --site-host <域名>          # 1. 生成配置
uv run python scripts/snapshot_statutes.py /tmp/fx.sqlite3  # 2. 法规库快照
# 3. 装 Docker + rsync，mkdir -p data runs exports，再传代码/配置/快照
docker compose -f deploy/compose.yaml build backend v3 frontend
docker compose -f deploy/compose.yaml up -d backend v3 frontend   # ⚠️ 先不起 caddy
docker compose -f deploy/compose.yaml exec -T backend .venv/bin/python scripts/preflight_public.py
docker compose -f deploy/compose.yaml up -d caddy        # 只有预检 ok:true 才执行这行
deploy/verify_deploy.sh https://<域名> --server ubuntu@<公网IP>
```

**为什么 Caddy 必须排在预检后面**：它是唯一把端口暴露到公网的容器。
配置不全时不起它，等于「站点根本没有公网入口」，而不是「起来了但坏了」——
后者会被搜索引擎和第一批用户看到。

## 四、要填的环境变量（一张表）

`SITE_HOST` 与 `ALLOWED_HOSTS` 填**同一个**域名，不带协议或路径。

### 站点

| 变量 | 值 |
| --- | --- |
| `SITE_HOST` | 正式域名，如 `law.example.com` |
| `ALLOWED_HOSTS` | 同上。**不要填 `*`** |

### 公开模式（两个后端共用，必须一致）

| 变量 | 值 | 说明 |
| --- | --- | --- |
| `AUTH_REQUIRE_LOGIN` | `1` | 打开登录门 |
| `AUTH_GUEST_MODE` | `1` | 无登录页，访客数据按 Cookie 隔离 |
| `AUTH_COOKIE_SECURE` | `1` | 只走 HTTPS |
| `GUEST_COOKIE_SECRET` | `openssl rand -hex 32` 的输出 | 两个后端**必须同一份**，否则隔离失效 |
| `GUEST_DAILY_LIMIT` | `5` | 每位访客每日付费调用上限 |
| `GUEST_GLOBAL_DAILY_LIMIT` | `30` | 全站每日上限 |

### 模型与检索

| 变量 | 值 |
| --- | --- |
| `MODEL_PROVIDER` | `deepseek` |
| `MODEL_BASE_URL` | `https://api.deepseek.com` |
| `MODEL_ID` | `deepseek-chat` |
| `MODEL_API_KEY` | 你的密钥 |
| `PKULAW_MCP_TOKEN` | 你的令牌 |
| `PKULAW_URL_*` | **14 个具名槽位，全部列在 `deploy/production.env.example` 里** |

⚠️ 别照着模板手工抄 `PKULAW_URL_*`。`config.yaml` 的 `mcp.endpoints` 按名字逐个引用它们，
少一个就少一个检索工具 —— 而且**不报错**，只是答案变差。
用 `deploy/render_env.py` 生成，它会对照 `config.yaml` 点名，少一个直接拒绝生成：

```bash
python3 deploy/render_env.py --site-host <域名>
```

⚠️ 密钥**只进后端环境**，不要写进前端变量、镜像层或 Git。
`.env*` 已在 `.gitignore` 里（`git check-ignore -v .env.production` 可自查）。

### 短信（见第五节，也是 preflight 的必过项）

| 变量 | 值 |
| --- | --- |
| `SMS_PROVIDER` | `pnvs`（或将来 `aliyun`）。**`mock` 会让预检直接判红** |
| `SMS_ALIYUN_ACCESS_KEY_ID` | RAM 用户 AccessKey |
| `SMS_ALIYUN_ACCESS_KEY_SECRET` | 同上 |
| `SMS_PNVS_SIGN_NAME` | 控制台「赠送签名配置」抄来的签名名 |
| `SMS_PNVS_TEMPLATE_CODE` | 控制台「赠送模板配置」抄来的模板编号 |

切到 `aliyun` 时把后两个换成 `SMS_SIGN_NAME` / `SMS_TEMPLATE_CODE`（AccessKey 不用换）。

### 不用手填的

`BACKEND_BASE_URL` / `V3_BACKEND_BASE_URL` 由 compose 按服务名设好（`http://backend:8010`、`http://v3:8011`），
别改成公网地址 —— 那样会把两个后端暴露出去。

## 五、短信通道（这一步不能跳过）

`preflight_public.py` 里有两条硬检查：`sms_channel_is_real` 与 `sms_channel_configured`。

**为什么卡这么死**：`SMS_PROVIDER=mock` 在公网上**不报错、看起来一切正常**，
它只是把**明文验证码**写进服务端日志和 `data/sms-outbox.jsonl` ——
等于「拿到日志的人能登录成任意手机号」。而本地开发长期停在 mock，上线时最容易忘的就是这一行。

开通步骤（个人实名即可，免资质、免签名、免模板）见
[短信通道开通清单.md](./短信通道开通清单.md)，这里只放最小摘要：

1. 阿里云账号完成**个人实名认证**
2. 号码认证服务控制台开通「**短信认证**」→ <https://dypns.console.aliyun.com/functions>
3. 从「赠送签名配置」「赠送模板配置」抄下**签名名**与**模板编号**（两者必须配套使用）
4. 买**短信认证套餐包**（⚠️ 与「短信服务」是两个独立产品，套餐包不互通）
5. 建 RAM 用户授 `AliyunDypnsFullAccess`，取 AccessKey
6. **把这几项填进本机的 `.env`**（不是直接填 `.env.production`）——
   `deploy/render_env.py` 会从本机 `.env` 把它们搬进 `.env.production`：

   ```
   SMS_PROVIDER=pnvs
   SMS_ALIYUN_ACCESS_KEY_ID=
   SMS_ALIYUN_ACCESS_KEY_SECRET=
   SMS_PNVS_SIGN_NAME=
   SMS_PNVS_TEMPLATE_CODE=
   ```

7. 重跑 `deploy/deploy.sh`，预检里的 `sms_channel_is_real` / `sms_channel_configured` 应转为 `true`

代价要说清楚：**短信里的发件人是阿里云赠送的名字，不是「法小智」**，且不可自定义。
要有自己的署名，只能等有企业主体后走 `aliyun` 通道。

> 另一个容易忽略的点：当前 `.env.production` 是 `AUTH_GUEST_MODE=1`（公开体验模式）。
> 在这个模式下后端会对 `/api/auth/*` 一律返回 404 —— **登录页与短信登录整体下线**，
> 访客靠 Cookie 自动获得独立身份。所以短信通道在 guest 模式下其实不会被用到；
> 它被预检卡住，是因为你随时可能切回登录模式，而那时候没有真实通道就是**安全漏洞**
> （`mock` 会把明文验证码写进日志）。

## 六、数据的边界（最容易出错的一步）

**只上传一样东西**：法规库快照。`deploy/deploy.sh` 已经自动化了这件事 ——
它用 SQLite backup API 打一致性快照，先传成 `.new` 再原子改名，
rsync 的排除表里也写死了所有不该传的东西。手工做就是：

```bash
uv run python scripts/snapshot_statutes.py /tmp/faxiaozhi-statutes.sqlite3
scp /tmp/faxiaozhi-statutes.sqlite3 USER@SERVER:~/faxiaozhi/data/statutes.sqlite3.new
# 在服务器上：mv -f data/statutes.sqlite3.new data/statutes.sqlite3
```

（先传 `.new` 再改名，是为了避免「传到一半，线上正好在读一个残缺的库」。）

**本机 `data/` 目录下这些东西一律不要上传**：

| 文件 | 为什么不能传 |
| --- | --- |
| `auth.sqlite3` | 本机账号库，云端要新建空的 |
| `v3.sqlite3` | 本机问答库 |
| `sms-outbox.jsonl` | **明文验证码**，本机调试用的 |
| `metrics.jsonl` | 本机指标 |
| `runs/` `exports/` | 本机的问答记录与导出文件，含私人内容 |

客户端（`frontend/`）若做过 `pnpm build`，`frontend/.next` 也不要上传，服务器上重建。

## 七、验收清单（起 caddy 之后逐条走）

先跑一遍自动的，它盯的是**坏了却不报错**的那几类：

```bash
deploy/verify_deploy.sh https://<域名> --server ubuntu@<公网IP>
```

- [ ] TLS 证书链校验通过、首页 200
- [ ] `is_stub == false`（模型没掉回 stub）
- [ ] `fzx_guest` Cookie 已下发（访客隔离生效）
- [ ] 匿名访问 `/api/admin/overview` 被拒（不是 200）
- [ ] **8010 / 8011 / 3001 从公网不可达**
- [ ] 见「你查不到但是真实存在的」：下面这些只能人工点

手工部分：

- [ ] 法规查找有结果
- [ ] 法律问答能出答案
- [ ] 类案研究能出结果
- [ ] 合同审查能上传并出结果
- [ ] 导出文件能下载
- [ ] **两位访客之间的数据互相看不到**（换浏览器或清 Cookie 验证）
- [ ] `docker compose -f deploy/compose.yaml logs --tail=100` 没有异常
- [ ] 清除 Cookie 后是全新访客身份（拿不回原数据，这是预期行为）

## 八、上线后仍挂着的事

- **线上法规库的每周自动更新尚未接通**。本机的核验任务只更新本机；
  同步到云端前，**不能声称线上法规库每周自动更新**。
- `data/`、`runs/`、`exports/` 要定期备份。备份 SQLite 走 SQLite backup API，
  不要直接复制正在写入的数据库文件。
- 当前是单实例设计（SQLite + 进程内会话），**不要起多副本**。
